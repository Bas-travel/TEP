# Security Audit

_Last reviewed: 2026-11-22. PASS is only recorded for controls exercised by an automated test or a command run._

## Verified controls
- Server-side RBAC: the role is read from the database on every request; `/partner/v1`, `/admin/v1`, `/staff/v1` reject other roles (403) and other partners' resources (404). Covered by the RBAC matrix in `portal_test.go`.
- JWT (HS256) access tokens, refresh-token rotation with reuse detection, PBKDF2 (120k iterations) password hashing — unit tests in `internal/auth` and `internal/api`.
- Suspension / role change revokes refresh tokens; suspended users cannot log in.
- Payment webhook: HMAC-SHA256 signature on the raw body, per-event de-duplication, idempotency keys on payments/bookings.
- Input validation, RFC 7807 errors, request body size limits, media upload type/size checks, in-process rate limiting, CORS configuration.
- All SQL is parameterised; multi-step operations run in transactions (`Repo.Tx`); every portal mutation writes an `audit_logs` row.
- Secrets: `.env` is git-ignored; secrets are generated by `scripts/setup-env.*`; the API refuses placeholder JWT/webhook secrets outside `dev` and a mock PSP in production.

## Not yet verified / not implemented
- Dependency and static scanning (`govulncheck`, `gosec`) — not run.
- Redis-backed rate limiting and refresh-reuse store.
- Secure token storage on devices; TLS/CORS settings for a real deployment.
- CSRF: not applicable to bearer-token APIs (no cookie auth); revisit if cookies are ever introduced.
- External penetration test, OWASP API Top 10 review, real webhook secret rotation.
